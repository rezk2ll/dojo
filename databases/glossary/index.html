2NF
Deuxième forme normale : avec une clé composée, aucune colonne n’est un fait sur une partie seulement de la clé.

3NF
Troisième forme normale : aucune colonne hors de la clé n’est un fait sur une autre colonne hors de la clé.
La normalisation
Accès concurrent
Plusieurs lecteurs et écrivains utilisent les mêmes données en même temps, sans les corrompre ni perdre d’écriture en silence.

ACCESS EXCLUSIVE
Le mode de verrou le plus fort. Il entre en conflit avec tous les autres, y compris les simples lectures. La plupart des formes d’ALTER TABLE le prennent, sauf mention contraire dans la doc.

Agrégat
Une fonction qui transforme beaucoup de lignes en une valeur : count, sum, min, max, avg. Sauf count, elles renvoient NULL quand aucune ligne n’arrive.

ANALYZE
Lit un échantillon aléatoire de la table et range des statistiques par colonne dans pg_statistic. L’autovacuum le lance en arrière-plan. L’échantillon fait 300 lignes par point de cible de statistiques : 30 000 lignes par défaut.
Statistiques du planificateur : comment PostgreSQL estime les lignes
Anomalie
Un changement que la forme de la table rend difficile ou faux : un fait à mettre à jour dans plein de lignes (mise à jour), impossible à ranger pour l’instant (insertion), ou qui disparaît avec une autre ligne (suppression).

Anti-jointure
Les lignes de A sans correspondance dans B : NOT EXISTS (...), ou une jointure gauche suivie de WHERE b.id IS NULL.

AOF
L’append-only file : chaque commande d’écriture est journalisée puis rejouée au démarrage pour reconstruire les données. Redis le livre désactivé.
Les bases clé-valeur
Archive WAL
Chaque segment de WAL terminé, copié en lieu sûr par archive_command. Avec une base backup, elle contient chaque changement depuis cette sauvegarde.

Autocommit
Sans BEGIN, PostgreSQL enveloppe chaque instruction dans sa propre transaction et la committe si elle réussit. Django tourne dans ce mode par défaut.
Transactions et savepoints
Autovacuum
Un processus lanceur et des processus workers qui vérifient chaque table et lancent VACUUM et ANALYZE quand assez de lignes ont changé.

B-tree
Un arbre de pages équilibré. Tous les chemins de la racine à une feuille ont la même longueur, donc chaque recherche coûte le même nombre de lectures de pages.

Base backup
Une copie de tout le répertoire de données, prise pendant que le serveur tourne (pg_basebackup, ou un outil comme pgBackRest). Le point de départ pour rejouer le WAL.

BRIN
Block Range Index. Garde un résumé, par exemple le min et le max, pour chaque groupe de 128 pages de la table par défaut. Il peut renvoyer des lignes qui ne correspondent pas (index lossy), donc l’exécuteur revérifie chaque ligne d’une plage retenue.
Types d’index : GIN, GiST, BRIN et Hash
Buffers
Les pages de 8 kB touchées par le nœud : hit dans le cache de PostgreSQL, read depuis l’OS ou le disque. Inclus par défaut avec ANALYZE depuis PostgreSQL 18.

Chargement par jointure
Une seule requête avec un LEFT OUTER JOIN qui ramène les colonnes liées. eager_load en Rails, select_related en Django.

Chargement paresseux
L’ORM ne charge une association que quand le code la lit pour la première fois. Rails et Django font ça par défaut. Dans une boucle sur N lignes, ça lance N requêtes.

CHECK
Une expression booléenne sur une ligne, testée à chaque insert et update : price > 0, ends_at > starts_at.

Checkpoint
Un point où toutes les pages modifiées en mémoire ont été écrites dans les fichiers de données. La reprise part du dernier, et le WAL plus ancien peut être recyclé. Toutes les 5 minutes ou tous les 1 GB de WAL par défaut.

L’ensemble des opérateurs qu’un index sait servir pour un type de colonne. Un index n’aide une clause WHERE que si elle applique l’un de ces opérateurs à la colonne indexée.

Clé d’idempotence
Une valeur unique que le client envoie avec une requête (souvent un UUID) pour que le serveur reconnaisse une nouvelle tentative de la même requête.

Clé d’idempotence
Une valeur que le client envoie avec sa requête pour qu’un nouvel essai soit reconnu. Une contrainte unique dessus transforme le deuxième essai en no-op (jour 23).

La colonne (ou les colonnes) qui décide dans quelle partition va une ligne. Souvent un timestamp pour range, une région ou un tenant pour list.

La colonne qui décide du shard d’une ligne. Citus l’appelle la distribution column. En général, c’est un id de tenant ou de client.

Clé de substitution
Une clé sans signification, fabriquée par la base : 1, 2, 3 tirés d’une séquence, ou un UUID aléatoire. Elle n’a jamais besoin de changer.

Clé étrangère
Une colonne dont la valeur doit correspondre à une clé d’une autre table. La base refuse une commande qui pointe vers un client qui n’existe pas.

Clé leader
Une clé dans le DCS qui nomme le primaire, rattachée à un bail (lease) avec un TTL. Qui la tient peut tourner en primaire ; si personne ne la renouvelle, elle disparaît.

Clé naturelle
Une clé tirée du monde réel : un email, un ISBN, « le ticket 42 de ce dépôt ». Les gens peuvent la changer, comme un client qui change d’email.

La ou les colonnes qui identifient une ligne. PostgreSQL exige qu’elles soient uniques et non nulles, et construit dessus un index B-tree unique.

Des tables shardées sur la même clé et les mêmes plages gardent les lignes qui vont ensemble sur le même nœud, donc les jointures et les transactions sur une clé restent locales.

Un index qui contient toutes les colonnes dont une requête a besoin. Avec INCLUDE, des colonnes en plus sont rangées dans les feuilles comme charge utile, pas comme clés de recherche.

Un index avec une clause WHERE : il ne contient que les lignes qui la vérifient. Plus petit, moins cher à mettre à jour, et utilisable seulement par les requêtes dont la condition implique cette clause.

Shard
Un morceau d’une table shardée, une table normale sur un serveur. Citus en crée 32 par table par défaut et les répartit sur les nœuds workers.
Le sharding
SKIP LOCKED
Une option de verrouillage pour SELECT : les lignes qu’une autre transaction a verrouillées sont laissées hors du résultat au lieu d’être attendues.
Une file de jobs dans la base
Snapshot
Trois choses : xmin (toute transaction plus ancienne est terminée), xmax (toute transaction à partir de là est invisible), et la liste des transactions encore en cours entre les deux.

Snapshot RDB
Une copie à un instant donné de tout le jeu de données dans un seul fichier compact, écrite par un processus enfant forké aux points de sauvegarde configurés.

Source de vérité
Les données à partir desquelles une copie est calculée. Si les deux ne sont pas d’accord, la source gagne et la copie est reconstruite.

Split brain
Deux serveurs acceptent tous les deux des écritures comme primaire. Leurs historiques divergent, et les commits du côté perdant sont perdus ou fusionnés à la main.

Des statistiques sur plusieurs colonnes, créées avec CREATE STATISTICS et remplies par ANALYZE : dépendances fonctionnelles, nombres de valeurs distinctes et listes MCV sur des groupes de colonnes.
Statistiques du planificateur : comment PostgreSQL estime les lignes
Stockage en colonnes
Chaque colonne est stockée à part. Une requête ne lit que les colonnes qu’elle nomme. DuckDB et ClickHouse fonctionnent ainsi.
Des colonnes pour l’analytique
Stockage en lignes
Toutes les colonnes d’une ligne sont côte à côte sur le disque. Rapide pour lire ou modifier une ligne entière. Le heap de PostgreSQL range les lignes ainsi.
Des colonnes pour l’analytique
Tâche outbox
Une ligne dans une table de tâches, écrite dans la même transaction que la commande. Un worker la prend plus tard, donc aucun e-mail ne part pour une commande annulée (jour 24).
Capstone : les données d’une boutique
Terme
Un nombre qui augmente à chaque élection. Chaque terme a au plus un leader. Un nœud qui voit un terme plus grand repasse follower.
Comment les réplicas se mettent d’accord
TOAST
Le stockage des grosses valeurs. Une ligne de plus de 2 ko environ voit ses gros champs compressés et, si besoin, déplacés par morceaux dans une table annexe.
Pages et lignes sur le disque
total_exec_time
La somme du temps d’exécution sur tous les appels. Trie dessus pour voir où le serveur passe son temps ; mean_exec_time seul cache les requêtes rapides lancées souvent.
Trouver les requêtes lentes
Transaction
Un groupe d’instructions que la base traite comme une seule unité. Elle finit par COMMIT (tout garder) ou ROLLBACK (ne rien garder).
Transactions et savepoints
Transaction de checkout
Une seule transaction qui crée la commande, ses lignes, la baisse du stock et la tâche de confirmation. Tout est validé, ou rien (jour 17).

Transaction en échec
Après une erreur dans une transaction, PostgreSQL refuse toutes les instructions suivantes jusqu’à un ROLLBACK, ou un ROLLBACK TO vers un savepoint.
Transactions et savepoints
tsquery
Des lexèmes reliés par &, |, ! et <->. @@ teste si un tsvector y correspond. :* demande une correspondance par préfixe.
La recherche plein texte
tsvector
Une liste triée de lexèmes, chacun avec ses positions dans le document et un poids optionnel. C’est ce que tu stockes et indexes.
La recherche plein texte
TTL
Un délai d’expiration sur une clé, posé avec EXPIRE ou SET ... EX. Redis appelle une telle clé « volatile ». Quand le temps est écoulé, la clé est supprimée.
Les bases clé-valeur
Tuple
Une version stockée d’une ligne, avec son en-tête. Un UPDATE écrit un nouveau tuple, donc une ligne peut en avoir plusieurs.
Pages et lignes sur le disque
UNIQUE
Deux lignes ne partagent jamais la même valeur dans ces colonnes. PostgreSQL l’impose avec un index B-tree unique.
Les contraintes : UNIQUE, CHECK et exclusion
Update gardé
Un UPDATE dont le WHERE vérifie aussi la règle, comme stock >= 1. S’il ne touche aucune ligne, la règle a échoué et la transaction est annulée.
Capstone : les données d’une boutique
Upsert
Insérer une ligne, ou la mettre à jour si une ligne avec la même clé existe. En PostgreSQL : INSERT ... ON CONFLICT ... DO UPDATE.
Upserts et nouvelles tentatives sans risque
USING / WITH CHECK
USING filtre les lignes existantes qu’une commande voit. WITH CHECK teste les nouvelles lignes qu’elle essaie d’écrire. Un check raté annule la commande.
Rôles, droits et sécurité au niveau des lignes
VACUUM
Retire les versions mortes qu’aucune transaction ne peut voir et marque la place comme libre pour de nouvelles lignes de la même table. Il ne bloque ni les lectures ni les écritures.
Lignes mortes et VACUUM
Verrou de ligne
Pris par UPDATE, DELETE et SELECT FOR UPDATE sur chaque ligne qu’ils touchent. Il bloque les autres écrivains et verrouilleurs de cette ligne, jamais les simples lecteurs. Relâché à la fin de la transaction.
Verrous et deadlocks
WAL
Write-ahead log : un enregistrement en ajout seul de chaque changement des tables et des index, dans les fichiers de pg_wal. Un changement est journalisé avant que la page qu’il décrit puisse arriver sur le disque.
Le journal d’écriture anticipée
Watchdog
Un minuteur, noyau ou matériel, qui redémarre la machine s’il ne reçoit pas de signal de vie à temps. Patroni compte sur lui quand le nœud ne peut pas se rétrograder.
Basculer sans split brain
Write skew
Deux transactions lisent les mêmes lignes, vérifient une règle, et chacune écrit une ligne différente. Chaque écriture est correcte seule. Ensemble, elles cassent la règle.
Niveaux d’isolation
xmax
L’identifiant de la transaction qui a supprimé ou remplacé cette version, ou zéro. Un xmax non nul sur une ligne visible veut en général dire que cette transaction n’a pas committé, ou a été annulée.

xmin
Une colonne cachée sur chaque version de ligne : l’identifiant de la transaction qui l’a insérée. Tu peux la sélectionner : SELECT xmin, xmax, * FROM orders.

Zonemap
Le min et le max d’une colonne dans un bloc. Un filtre qui tombe hors de l’intervalle saute le bloc sans le lire. On dit aussi index min-max.
