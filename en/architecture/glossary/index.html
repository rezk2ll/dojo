Glossary

Adapter
The code that implements a port for one technology: local disk, S3, Google Cloud Storage. The adapter depends on the port, and the core does not know which adapters exist.
Ports and adapters: one core, many backends
Adapter
A wrapper that makes an object fit an interface it was not written for. A decorator keeps the interface and adds behavior; an adapter changes the interface.
Design patterns: named shapes you already use
ADR
Architecture Decision Record: a short file with Title, Status, Context, Decision and Consequences (Michael Nygard, 2011).
Architecture decision records: writing down the why
Aggregate
A cluster of objects changed as one unit, through one root. Its invariants, the rules that must always hold, are checked inside it.
DDD building blocks: inside one context
Allowlist
A rule that forbids everything except what it names. Known exceptions are listed one by one, so a new violation cannot slip in unnoticed.
Fitness functions: decisions that check themselves
Altitude
How much detail an audience needs to act on a decision.
One decision, three audiences
Anti-corruption layer
A translation layer in the downstream context that rewrites the upstream model in its own terms, so the rest of its code never sees the foreign words.
Bounded contexts and context maps
Architect Elevator
Hohpe's image: the architect rides between the IT engine room and the executive penthouse, and keeps the two connected.
One decision, three audiences
Architecture
The decisions that are hard to change later and shape everything else: how the system is split, where state lives, how parts talk.
Software architecture: the decisions that are expensive to change
Assumption
The rules allow assumptions about technologies you do not know well, as long as you define them clearly when you present. Bad assumptions, never checked with the customer, earn a thumbs down.
Your first kata: a whole design in 15 minutes
Asynchronous job
The caller gets an answer before the work is done. The work runs later, from a queue such as Sidekiq's in Redis, and its errors arrive by another path or not at all.
Sync calls vs async jobs
At-least-once
A message is never lost once the broker accepts it, but may arrive twice. The consumer confirms only after the work is done, and dedupes.
Messaging: queues, delivery guarantees and dead letters
Authentication
Checking who the caller is: a password once, then a token on each request.
Gateways, tokens and SSO
Authorization
Deciding what this caller may do on this data. It needs the data's rules, so the owner of the data does it.
Gateways, tokens and SSO
Backfill
Filling the new shape for rows written before it existed. Inside the migration, as a background job in batches, or not at all if the code reads "empty" safely.
Schema and data migrations
Backward-compatible change
Old consumers keep working without a change on their side: a new endpoint, a new optional field. Removing, renaming or retyping a field, or giving it a new meaning, is a breaking change.
API design and versioning
Blocking question
A question that must be answered before the design is accepted. Mark it, so the author finds it among the small ones.
Reviewing a design: scenarios, doors, failures
Boundary
The line between what your team owns and what others own. You can change what is inside it, and you have to agree with another team or company to change what is outside.
The context diagram: your system as one box
Bounded context
A boundary inside which every term has exactly one meaning. Often one service or one team.
Bounded contexts and context maps
Bulkhead
Separate pools, queues or limits per kind of work, so one kind can fill up without starving the others. Named after the walls in a ship's hull.

C4
Four zoom levels for diagrams: Context, Containers, Components, Code. You rarely need to draw the fourth.
The context diagram: your system as one box
Capability negotiation
The server lists what it supports, and the client checks the list before it uses a feature. One client then works with servers of different ages.
API design and versioning
Chain of responsibility
A request passes through a list of handlers in order. Each may change it, pass it on, or stop it.
Design patterns: named shapes you already use
Characteristic
A quality the system must have that is not a feature: latency, throughput, availability, security… Often called an "-ility".

Circuit breaker
After too many failures, stop calling a dependency for a while and fail at once. Then let a few trial calls through to see if it healed.
Resilience: stop one failure from spreading
Cohesion
How closely the parts of one module belong to the same job. Low cohesion: a module that does two unrelated things.

Compensating action
A new action that undoes the effect of an earlier one: release the stock, refund the card. It differs from a rollback because other services may already have seen the first step.

Competing consumers
Several consumers read from one queue, and each message goes to only one of them. More consumers handle more messages per second, but messages can finish out of order.

Composition root
The one place allowed to know both an interface and its implementation, to wire them together. Here, the Hilt DataModule.

Conformist
The downstream context (the one that receives) adopts the upstream model as it is, because it has no say or translating costs too much.

Consequences
Everything that follows from the decision, the good and the bad. If you listed no downside, look again (first law).

Consumer-driven contract
Each consumer writes down the part of a message or API it actually reads, and the producer runs those expectations in its own CI. The Pact tool implements this pattern.

Container (C4)
Something that must be running for the system to work, as one process or one data store: a server app, a database, a browser app, a worker.

Container diagram
C4 level 2. The containers inside your system, what technology each one is, and how they talk.

Contract test
A test that checks a double against the real thing it stands for. Fowler: "These check that all the calls against your test doubles return the same results as a call to the external service would."

Copy
Data you keep but do not own. It can go stale, so you must know who updates it, and you never edit it yourself.

Core
What makes you different from competitors. It is complex and changes often, so you build it in-house with your best people.

Coupling
How much a module must know about another to work. More coupling means a change in one forces a change in the other.

CQRS
Command Query Responsibility Segregation: one model to change data, another to read it. Martin Fowler credits Greg Young with describing it. It does not require event sourcing.
CQRS and event sourcing
Data flow diagram
Boxes for processes and stores, arrows for data, outside parties drawn apart. The map a threat model is done on.
Threat modeling
Dead set
Where Sidekiq keeps a job after its last failed retry, so a person can look at it. A job can opt out and be dropped instead.
Sync calls vs async jobs
Dead-letter queue (DLQ)
The queue where the broker puts messages that failed too many times. Someone must get an alert, read each message, and decide what to do with it.
Messaging: queues, delivery guarantees and dead letters
Decorator
A class that implements the port and wraps other implementations of the same port, adding one behavior such as copying every upload to a second store.
Ports and adapters: one core, many backends
Dependency rule
Here: UI depends on domain, and domain depends on data. No import points up, so the lowest layer knows least about the others.
Layers: imports only go one way
Deployment diagram
Where container instances run, on which machines or clusters, for one environment.
Deployment: boxes on machines
Deprecation
Saying that something will go away while it still works. Then count who still calls it, and remove it on a date (the sunset).

Design review
Reading a proposal to find the decisions that are expensive to change, like a default behavior other teams build on.
Reviewing a design: scenarios, doors, failures
Directory placement
A lookup table records where each key lives, instead of computing it from a hash. Easy to add a node to, but the table itself must always be readable.

Drift
The code slowly moving away from a decision, one reasonable-looking change at a time.

Driving
The few characteristics that shape the design. Keep this list as short as you can, three at most.

Dual write
Your code writes to two stores one after the other, with nothing making both succeed or both fail.

Event-driven
Parts react to events instead of calling each other directly. Good for decoupling, harder to trace and test.

Hop

Try again, waiting longer after each failure, so a struggling service gets room to recover. Jitter adds a random bit to each wait, so a thousand clients that failed together do not all retry in the same second.
